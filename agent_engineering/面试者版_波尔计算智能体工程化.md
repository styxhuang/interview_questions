# 面试小作业　接手并改进一个波尔计算智能体

## 背景

团队已经实现了一个可以运行的波尔计算智能体原型。用户可以用自然语言提出计算需求，智能体会选择 Skill 和工具，通过 Bohrium CLI 提交或查询计算任务，并通过 FastAPI 对外提供服务。项目使用 MySQL 保存部分运行数据。

当前原型已经能用 mock CLI 完成简单演示，但在可靠性、可恢复性和评测方面仍有明显改进空间。你将接手配套的 starter repo，在有限时间内完成一次有依据的工程审计和框架优化，并把优化后的系统接到一个真实 Bohrium 任务上。

本作业允许并鼓励使用 DSH、Codex、Claude Code 或其他开发智能体。我们会关注你怎样让开发智能体理解项目、怎样检查生成结果，以及你能否对最终系统作出独立判断。

## 作业目标

完成本作业后，你应当交付一个仍然保持最小规模、但更可靠且可以评测的智能体服务。

我们主要观察以下能力。

1. 使用开发智能体理解和修改陌生项目。
2. 识别工程问题，并根据影响和时间决定优先级。
3. 理解 Model、Harness、Skill 与 Tool 的职责边界。
4. 处理长时间运行的外部计算任务，包括超时、重复提交和服务恢复。
5. 用可复现评测说明修改是否有效。

## 建议开始方式

仓库提供 `INITIAL_PROMPT.md`。建议把它作为第一条消息交给你使用的开发智能体，用于建立项目地图、可复现基线和 `workpack/` 题包工作区。你可以修改 Prompt 以适应自己的工具，但需要保留密钥隔离、外部操作批准和实验记录要求。

## 任务一　建立基线并完成工程审计

先按仓库说明启动服务并运行现有基础测试。随后建立自己的评测框架，再运行 baseline。保存以下信息。

- 运行命令和环境说明
- 使用的模型、参数与代码版本
- baseline 的逐题结果和汇总指标
- 失败或无法复现的部分

随后提交 `ENGINEERING_REVIEW.md`。审计应包含至少 5 个有实际影响的问题，每个问题写清以下内容。

| 项目 | 说明 |
| --- | --- |
| 现象与证据 | 从代码、日志、数据库或评测结果中看到什么 |
| 影响 | 会导致什么错误、风险或维护成本 |
| 优先级 | 建议使用 P0、P1、P2，或自定义清晰标准 |
| 处理决定 | 本轮修复、暂缓或只给方案 |
| 验证方式 | 怎样证明问题已经解决 |

问题数量本身不加分。我们更关心证据是否充分，优先级是否合理，以及你是否能在时间限制内控制修改范围。

## 任务二　优化智能体框架

你需要对 Model、Harness、Skills 和 Tools 的协作方式作出实质改进。Harness 为必做项，其余部分根据审计结果安排，但最终系统需要满足下面的行为要求。

### Model

- Model client 可以替换，业务代码不直接依赖某个厂商 SDK。
- 模型产生的 action 或 tool call 有明确结构，并在执行前校验。
- 非法参数、未知工具和无法解析的输出不能直接触发外部操作。
- 测试可以使用 FakeModel、录制回放或等价方式离线运行。

这里的 Model 优化不等同于更换更大的模型。上下文组织、结构化输出、失败处理和调用成本都可以成为优化对象。

### Harness

Harness 至少需要负责以下行为。

- 限制单次运行的最大步数和重试预算。
- 根据策略决定模型当前可以调用哪些工具。
- 校验状态转换，并记录模型调用、Skill 加载和工具执行事件。
- 区分可重试、不可重试和结果未知的错误。
- 对可能产生重复副作用的操作进行幂等控制或事后对账。
- 在服务重启后恢复未完成的 run。
- 在取消任务、提高资源规格等高风险操作前等待用户批准。
- 把外部日志和工具返回视为不可信数据，不能让其中的文字改变系统权限。

你可以使用现有 Agent 框架，也可以保留项目中的自研循环。请在报告中说明选择依据和约束。

### Skills 与 Tools

项目至少应包含以下三类能力。

- 提交计算任务
- 查询和监控任务
- 分析失败日志并给出下一步建议

Skill 应表达可复用的任务知识和操作流程。Tool 负责执行有明确输入输出的动作。请避免把所有 Skill 内容无条件加入每一轮上下文。

请让 Skill 至少具备可识别的名称和版本，并记录每次运行实际加载了哪些 Skill。若你为 Skill 增加工具权限声明、适用条件或测试，也请在报告中说明。

## 任务三　用 FastAPI 与 MySQL 组成完整服务

项目至少需要提供以下接口，路径可以等价调整。

```text
POST /v1/runs
GET  /v1/runs/{run_id}
POST /v1/runs/{run_id}/approve
POST /v1/runs/{run_id}/resume
```

`POST /v1/runs` 应尽快返回可查询的 `run_id`，不应一直占用请求直到远端计算结束。调用方需要能够查询当前状态、最终回答和关键事件。

MySQL 应当保存足以支持恢复和审计的数据。具体表结构由你设计，但至少需要覆盖下列信息。

- Agent run 与当前状态
- 模型、Skill 和工具事件
- 本地 run 与波尔计算任务的映射
- 幂等标识
- 待批准或已经处理的操作

进程内对象可以作为缓存，不能成为唯一状态来源。请提供 migration 或等价的建表方式。

## 任务四　接入真实 Bohrium CLI

你必须从 [Bohrium 注册页](https://www.bohrium.com/login?pageType=register)创建账号并登录，创建或加入一个可以提交任务的项目，取得自己的 AccessKey，并在可信终端安装 `@dptech-corp/bohr-cli`。软件包安装后的命令名是 `bohr`。

认证信息不得提交。禁止把 AK 放进开发智能体对话、Prompt、日志、截图、fixture、报告、`.env` 提交或 Git 历史。只在可信终端使用 AK 完成 `bohr auth login --ak '<your-access-key>'`；如果当前 CLI 支持浏览器 SSO，也可以运行 `bohr auth login`。只记录认证是否成功，不记录或回显 AK。

新账号可能带有平台赠送的体验金，具体金额和适用范围以账号实际显示为准。提交前必须执行 `bohr billing balance` 和 `bohr billing pricing`，确认可用体验金/余额、当前单价和预计最长运行时间。不得为完成本题自行充值；如果体验金不足、计价无法确认或预估费用超出可用额度，应停止提交，保留脱敏证据并联系面试官。

框架需要同时支持 mock 与真实 CLI。mock 用于离线回归，最终验收必须包含至少一个最低成本的真实 CPU 作业。适配器至少支持以下动作。

```text
submit
status
logs
cancel
download
```

真实联调必须完成 `submit -> describe/status -> log -> download -> 结果校验` 闭环，并把本地 run 与真实 job ID 关联起来。只允许提交一次单节点、最低规格 CPU smoke job，最长运行时间不超过 2 分钟；不得为了本题申请 GPU 或高规格资源。首次真实运行后保存脱敏 replay，后续评测不得反复消费真实算力。

mock CLI 会模拟正常完成、提交超时、运行失败和输出格式变化等情况。你的实现不应通过修改 mock CLI 或硬编码 case id 来绕过这些情况。

调用外部命令时需要妥善处理参数、退出码、标准输出、标准错误和超时。请避免把用户输入直接拼接成本地 shell 命令。

提交 `REAL_BOHRIUM_REPORT.md`，记录 CLI 版本、执行时间、project ID、job name、job ID、镜像、机型、提交前后的余额类别、当前单价、预计/实际费用、最终状态、脱敏后的命令结果和下载文件 SHA-256。金额可以按公司要求脱敏，但必须足以证明没有超出预算；报告中不得出现 AK。

## 任务五　自行建立前后对比评测框架

starter repo 不提供现成 eval runner、case 或 scorer。你需要自行决定测试框架、case schema、fixture/replay 机制、评分器和报告格式，并说明选择依据。

使用同一模型、同一模型参数和同一组输入，对修改前后的系统分别运行评测。每个 case 独立执行，避免上一题的上下文影响下一题。

至少自行设计 8 个有区分度的 case，覆盖正常任务、输入校验、外部失败或结果未知、重复副作用、安全或批准、服务恢复，以及至少一个真实 Bohrium 场景。真实场景应保存脱敏 replay，便于在不反复消费算力的情况下回归。

每个 case 都应包含可执行或可程序判断的 gold。不要只判断最终自然语言回答是否相似。建议同时检查以下结果。

- 实际创建了几个计算任务
- 工具参数和调用顺序是否满足约束
- 最终 run 与 compute job 的状态
- 是否发生重复提交或未经批准的操作
- 数据库和 trace 中是否存在必要事件

至少报告以下指标。

| 指标 | 含义 |
| --- | --- |
| 任务完成率 | 是否达到场景要求的最终状态 |
| 工具调用合法率 | 工具和参数是否通过 schema 与策略校验 |
| 重复提交率 | 同一个逻辑请求是否创建多个远端任务 |
| 非授权操作率 | 是否执行了等待批准或明确禁止的动作 |
| 故障恢复率 | 超时、重启或中断后能否回到正确状态 |
| 无效循环率 | 是否出现没有新信息的重复模型或工具调用 |
| Trace 完整率 | 关键决策和副作用是否可以追踪 |

提交 baseline 与优化后的逐题结果、汇总指标和错误分析。总分提高并不能代替错误分析。请指出提升来自哪里，仍然失败的 case 卡在哪一层。
